Supersedes the reserve and `bidLock` parts of 2026-11-13-squad-rules-frozen-in-go-live-event (the rules are still frozen in the go-live event).
The reserve is exact. `SquadReserve` groups the players still to come by role and restricted categories and searches how many to take from each group, cheapest first within a group. The search respects role minimums, the squad minimum and maximum, and every category cap. Lots are sorted by base price once at go-live (`AuctionState.lotsByPrice`), so the bid path never sorts. Groups and counts are small, so the search costs about as much as the greedy pick did.
If the pool cannot fill the squad, the reserve covers only what the pool can still supply, and a franchise may always bid toward a legal squad. A bid is refused at any price (`no_room`) only when winning the lot leaves the squad less complete than passing it: the lot takes the last place, or a capped place that a needed role must use.
Each `BidGuard` states one limit per lot (`limit`: reason, role or category, frozen cap, `above` = the highest bid it allows), and `check` is derived from it. The state sends the viewer every limit in guard order (`bidLimits`). The client shows the first limit that refuses the next bid, so the dock names the same rule the server would. A rival's bid patch then locks the dock with no reread, because limits change only when a lot closes.
Rejected: a greedy estimate (it refused bids a legal squad could afford); refetching state on every rival bid (one GET per manager per bid, plus a window where the old lock still shows); a single `bidLock` for the current next bid (it goes stale as soon as the price moves).
